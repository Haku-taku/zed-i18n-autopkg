# zed-i18n-autopkg

Arch Linux packaging for [LI-NA/zed-i18n](https://github.com/LI-NA/zed-i18n), produced
automatically from upstream releases.

## Why this repository exists

`zed-i18n` addresses every translation by byte offset in one pinned Zed revision, so a
package cannot move `pkgver` independently of the i18n revision it was cut from. Upstream
already publishes that combination as a release: `v<zed-version>-i18n.<rev>`, with
prebuilt Linux tarballs attached.

So nothing here compiles, and nothing here tracks upstream *source*. The workflow watches
upstream **releases**, takes the two Linux tarballs, relocates the bundle into the FHS
layout the official Arch `zed` package installs, and publishes:

- `zed-i18n-linux-x86_64-pkgdir.tar.gz`
- `zed-i18n-linux-aarch64-pkgdir.tar.gz`
- `PKGBUILD` — with `pkgver`, `_i18nrev`, `url` and both `sha256sums` rendered from the
  trees beside it

The release is the deliverable. Nothing is pushed to the AUR: take `PKGBUILD` from the
release and build with `makepkg` wherever you package.

The consequence worth stating plainly: **there is no upstream branch to merge.** A
release is consumed as assets, so a change upstream cannot conflict with anything here.

## Setup

No secrets are required: the workflow uses the built-in `GITHUB_TOKEN` to read upstream
releases and to publish its own.

```bash
gh workflow run package-release.yml -f dry_run=true   # stage without publishing
gh workflow run package-release.yml                   # package the newest upstream release
```

It then runs hourly on its own. An upstream release is packaged within the hour.

## Installing the result

```bash
gh release download v<zed-version>-i18n.<rev> -p PKGBUILD
makepkg -si
```

`makepkg` reads `source_x86_64` / `source_aarch64` from the rendered PKGBUILD, which point
back at the release assets, so no `.SRCINFO` and no AUR step is involved.

## What is vendored

`tools/zed_i18n/` and `packaging/arch/PKGBUILD` are copied from
`Haku-taku/zed-i18n` at the commit this repository was seeded from. Only the modules the
staging step needs are here:

```
tools/zed_i18n/{arch,deb,packaging,linux_abi,config,linux_builder}.py
tools/zed_i18n/arch_overlay/zed.metainfo.xml.in
packaging/arch/PKGBUILD
```

`linux_abi.py` imports `tools.zed_i18n.linux_builder` by absolute path, so the
`tools/zed_i18n/` layout has to be preserved — flattening the package breaks the import.

Re-copy them when the staging rules change upstream; that is a copy, not a merge.

## What the staged tree contains

Identical to what the fork produced, because it is the same code: `arch.py` is copied
byte-for-byte, and `tests/test_layout.py` asserts the exact member set.

```
usr/bin/zeditor                                     <- bundle bin/zed
usr/lib/zed/zed-editor                              <- bundle libexec/zed-editor
usr/share/applications/dev.zed.Zed.desktop          <- rewritten: Exec=zeditor
usr/share/icons/hicolor/<size>/apps/zed.png         <- from the bundle
usr/share/bash-completion/completions/zeditor       <- generated by running the CLI
usr/share/fish/vendor_completions.d/zeditor.fish    <- generated
usr/share/zsh/site-functions/_zeditor               <- generated
usr/share/metainfo/dev.zed.Zed.metainfo.xml         <- rendered from arch_overlay/
```

The bundle's `lib/*.so` and `licenses.md` are dropped on purpose — an Arch package links
against the distribution's libraries.

Completions are not in the upstream tarball; they exist only because staging executes the
bundled CLI under the installed name and captures what it prints. That is why the runner
must match a downloaded architecture.

## Caveats

- **`pkgver` comes from the tag, not from `config/project.toml`.** They agree today
  because upstream derives the tag from that file. If that ever stops holding, the
  package would silently mis-apply translations; `scripts/package_release.py` rejects any
  tag that is not `v<digits.digits.digits>-i18n.<digits>` rather than guessing.
- **Completions are generated by running the binary.** `generate_completions()` executes
  the bundled CLI under the name the package installs (`zeditor`), so the runner must
  match one of the downloaded architectures. `ubuntu-24.04` matches x86_64.
- **Upstream pre-releases are ignored** (`prerelease == false` in the detection query).
